PROJECT INTRO

项目介绍

基于 Unity DOTS/ECS 的大规模群体跟随与弹幕系统。场景中批量生成代理单位，它们围绕主角保持指定距离，通过共享 Flow Field 获取全局移动方向，并结合 KNN 快速邻居查询与 ORCA 局部避障，实现群体单位的自然分流与实时避碰。ECS 对象池驱动的弹幕系统实现代理可批量发射投射物，投射物生命周期结束后回收到池中复用，减少高频创建和销毁带来的性能开销。整个场景通过 ECS 数据导向设计和 Job 化计算，支持大量单位同时移动、避障与弹幕射击。

以实际群体导航流程为线索，完整梳理 Unity ECS 的数据模型、并行计算、结构性变更与系统调度。

01 / FOUNDATION

ECS 与数据导向设计

ECS（Entity Component System）将数据与行为分离：Entity 是对象的唯一 ID，不包含数据和逻辑；Component 用结构体保存实体状态；System 查询特定组件，并批量处理符合条件的实体。

维度MonoBehaviourECS
内存布局对象散落在堆上（AoS）同类组件连续排列（SoA）
缓存命中存在指针跳跃可线性遍历，命中率更高
并行能力通常受主线程限制可通过 Job System 并行
GC 压力常使用 class 引用，较高主要使用值类型与 Native 集合，较低

02 / CONVERSION

Authoring 与 Baker：从 GameObject 到 Entity

场景阶段由 Authoring 在 Inspector 提供网格尺寸、节点数量、偏好距离与重建间隔等配置入口；Baker 再将这些参数烘焙为 ASGrid、ASFlowFieldConfig 等 ECS 组件，以及网格节点、积分场、流场方向等动态缓冲区。

职责划分Authoring 面向编辑体验；Baker 面向运行时数据布局。这样系统和 Job 可以直接读取紧凑的组件与缓冲区，而不依赖 GameObject 层级。

03 / SHARED NAVIGATION

ISystem、ECS 单例与共享 Flow Field

GroupTarget 场景只保留一个携带 ASGrid 的 Grid Entity。FlowFieldSystem 读取这个单例上的网格、配置、状态与流场缓冲区，根据主角位置计算一次全局方向场；之后每个 Agent 都只读同一份结果来生成自己的期望速度。

Grid Entity→FlowFieldSystem→Integration / Direction Buffers→所有 Agent 共享读取

这种设计将全局寻路成本从“每个 Agent 各算一次”变为“每次重建只计算一次”，并让网格配置和系统行为保持解耦。

04 / PARALLELISM

Burst、IJobEntity 与并行实体处理

FlowFieldSteeringJob 以只读 NativeArray 接收积分场和方向场数据。BurstCompile 将数值计算编译为高性能原生代码；IJobEntity 自动匹配拥有 ASFlowFieldAgent、ASAgent、ASPreferredVelocity 与 LocalTransform 的实体；ScheduleParallel 将不同 Agent 的期望速度计算分发到多个工作线程。

并行写入原则共享流场始终只读；每个 Job 只写回自身的 ASPreferredVelocity，因此能安全地对大量代理并行执行。

05 / DATA ACCESS

查询缓存与随机访问

EntityQuery 用于确定当前帧要处理的实体集合，例如同时拥有 LocalTransform、ASAgent、ASAvoidanceAgent 与邻居缓冲区的代理；ComponentLookup<T> 适合在已知 Entity 时随机读取固定组件；BufferLookup<T> 则访问每个 Agent 长度可变的邻居列表。

EntityQuery“本次处理哪一批实体？”
ComponentLookup“已知 Entity，如何读固定组件？”
BufferLookup“已知 Entity，如何读可变列表？”

KNN 找到相邻 Agent 后，将结果写入该实体专属 DynamicBuffer，为之后的 ORCA 局部避障提供数据。

06 / STRUCTURAL CHANGE

EntityCommandBuffer：延迟结构性变更

批量生成 Agent 或投射物时，Instantiate、AddComponent 等操作会改变实体组件集合，使 Entity 迁移到其他 Chunk；若在遍历或 Job 执行期间立即修改 EntityManager，查询、DynamicBuffer 引用与 Job 访问都可能失效。

记录 Instantiate / AddComponent→本轮逻辑完成→ECB Playback→统一创建与标记实体

因此系统先把命令写入 EntityCommandBuffer，再在安全时机统一 Playback。对象池中的投射物回收与复用也沿用这一批量、延迟的结构性变更思路。

07 / REBUILD LIFECYCLE

流场重建请求实体

障碍物扫描完成、代理净空变化或主角进入新网格时，相关系统不直接重建流场，而是创建或更新一个 FlowFieldRebuildRequest Entity。请求携带 Grid Entity、重建原因与最新目标格；同一 Grid 同时最多保留一个请求，多个来源会合并到它上面。

Topology
障碍或网格可通行性变化Clearance
代理尺寸或净空变化TargetCell
目标进入新网格合并为一个 Request
由 FlowFieldSystem 消费后销毁

Topology 与 Clearance 会立即触发重建；仅 TargetCell 的请求遵守节流间隔，并在等待期间持续合并最新目标。这样生产者与消费者解耦，生命周期也更清晰。

08 / UPDATE ORDER

GroupTarget 的 System 执行顺序

系统通过 UpdateInGroup、UpdateAfter 与 UpdateBefore 声明依赖，确保所有计算消费正确版本的数据。

  1. CheckObstaclesSystem扫描障碍，更新网格节点，发出 Topology 重建请求。
  2. FlowFieldClearanceSystem根据障碍与代理尺寸构建安全可通行格。
  3. MainRoleMovementSystem更新主角最新位置。
  4. FlowFieldSystem消费请求，使用最新目标与 Clearance 重建流场。
  5. FlowFieldSteeringSystem读取流场，计算每个 Agent 的期望速度。
  6. AgentNeighbourSystem收集邻居，为 ORCA 避障准备数据。
  7. AgentAvoidanceSystem基于邻居与期望速度计算实际避障速度。
  8. FlowFieldAgentMovementSystem移动实体，并做最终的静态障碍安全处理。
