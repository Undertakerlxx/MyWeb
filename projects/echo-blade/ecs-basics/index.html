UNITY ECS / FOUNDATIONS

ECS架构基础

DATA · JOBS · FLOW FIELD

ECS（Entity Component System）是一种数据导向设计模式：让数据与行为分离，以更高效的方式处理大量实体。以下内容对应群体导航系统从配置、流场构建到批量移动的完整基础架构。

01. CORE MODEL

Entity、Component 与 System

Entity对象的唯一 ID；本身不包含数据或逻辑，只负责标识。
Component使用 struct 保存实体状态；不包含行为函数。
System查询特定组件，并批量处理符合条件的实体。

与 MonoBehaviour 的本质区别

维度MonoBehaviourECS
内存布局每个对象散落在堆上（AoS）同类组件连续排列（SoA）
缓存命中较差，存在指针跳跃很好，可线性遍历
多线程通常受主线程限制可通过原生 Job System 并行
GC 压力较高，常使用 class 引用较低，主要使用值类型与 Native 集合
02. AUTHORING TO DATA

Authoring 与 Baker：从 GameObject 到 Entity

在 Authoring 组件中配置场景参数，再由 Baker 将配置烘焙为 ECS 组件与缓冲区。ASFlowFieldConfig 挂在网格 Entity 上，保存整个 GroupTarget 场景共享的流场寻路配置。

public struct ASFlowFieldConfig
    : IComponentData { }
public class GridAuthoring : MonoBehaviour {
  public int NodeXCount;
  public int NodeYCount;
  public float NodeSize;
}
public override void Bake(GridAuthoring authoring) {
  Entity entity = GetEntity(TransformUsageFlags.Dynamic);
  AddComponent(entity, new ASGrid { /* ... */ });
  AddComponent(entity, new ASFlowFieldConfig { /* config */ });
  AddBuffer<ASGridNodesBufferComponent>(entity);
  AddBuffer<ASIntegrationFieldCell>(entity);
  AddBuffer<ASFlowDirectionCell>(entity);
}

职责划分 Authoring 负责 Inspector 中易用的配置入口；Baker 将这些配置转换为 ECS System 与 Job 高效读取的组件和缓冲区。

03. SHARED FLOW FIELD

ISystem、ECS 单例与共享流场

FlowFieldSystem 每帧检查是否需要重建流场，并计算每个格子的代价与行进方向；系统本身不保存网格数据，而是从 Entity 读取。GroupTarget 场景只有一个带 ASGrid 的 Grid Entity，因此可通过 GetSingletonEntity 取得唯一网格实体。

Entity gridEntity = SystemAPI.GetSingletonEntity<ASGrid>();
ASGrid grid = SystemAPI.GetComponent<ASGrid>(gridEntity);
ASFlowFieldConfig config =
    SystemAPI.GetComponent<ASFlowFieldConfig>(gridEntity);

04. PARALLEL JOBS

Burst、Job 与并行实体处理

系统将流场 Entity 上的缓冲区转换为 Job 可读取的 NativeArray，再以 FlowFieldSteeringJob 异步并行计算每个 Agent 的期望速度。

[BurstCompile]
private partial struct FlowFieldSteeringJob : IJobEntity {
  [ReadOnly] public NativeArray<ASIntegrationFieldCell> Integration;
  [ReadOnly] public NativeArray<ASFlowDirectionCell> Directions;
  public void Execute(in ASAgent agent,
      ref ASPreferredVelocity preferredVelocity,
      in LocalTransform transform) { /* write own velocity */ }
}
state.Dependency = new FlowFieldSteeringJob { /* ... */ }
    .ScheduleParallel(state.Dependency);

05. LOOKUPS & CHANGES

查询缓存、随机访问与延迟结构性变更

EntityQuery确定本次处理哪一批实体：例如同时拥有 LocalTransform、ASAgent、ASAvoidanceAgent 与邻居缓冲区的 Agent。
ComponentLookup<T>已知一个 Entity 时，快速随机访问固定组件，例如 LocalTransform、ASAgent。
BufferLookup<T>已知一个 Entity 时，访问其长度可变的 DynamicBuffer 邻居列表。

KNN 算出某个 Agent 的邻居后，写入其专属动态缓冲区，为 ORCA 局部避障提供输入。批量生成 Agent 与投射物则使用 EntityCommandBuffer：Instantiate 和 AddComponent 都是结构性变更，直接在循环中修改 EntityManager 可能移动 Chunk、使查询或 Job 引用失效。

计算本次生成数量→ecb.Instantiate / ecb.AddComponent
仅记录命令→全部 Agent 命令完成→ecb.Playback
统一创建与标记

实际价值 延迟并批量执行结构性变更，使新生成实体安全进入流场系统；对象池中的投射物回收与复用同样避免了高频创建、销毁带来的开销。

请求实体的职责与数据

障碍扫描完成、流场代理尺寸变化或目标进入新的网格时，相关系统不直接重建流场，而是创建或更新一个 FlowFieldRebuildRequest Entity。Grid 的 ASFlowFieldState.PendingRebuildRequest 保存请求引用，确保每个 Grid 同一时刻最多只有一个请求。

ASFlowFieldRebuildRequestTag：表示存在待处理的流场重建请求。
ASFlowFieldRebuildRequestData保存 Grid Entity、重建原因、最新目标位置与目标格。
PendingRebuildRequest由 Grid 保存临时请求引用，保证请求唯一性。

03

GROUPTARGET / UPDATE PIPELINE

System 执行顺序

ORDER GUARANTEES DATA CORRECTNESS

通过 UpdateInGroup、UpdateAfter 与 UpdateBefore 声明系统依赖：先更新障碍和安全通行数据，再使用主角最新位置构建流场；随后计算期望速度、收集邻居、执行 ORCA 避障，最后安全移动实体。

INPUTBUILDSTEERAVOIDMOVE
01CheckObstaclesSystem扫描障碍，更新网格节点，发出 Topology 重建请求。
02FlowFieldClearanceSystem根据障碍与代理尺寸构建安全可通行格。03MainRoleMovementSystem更新主角最新位置。
04FlowFieldSystem消费请求，使用最新目标与 Clearance 重建流场。
05FlowFieldSteeringSystem读取流场，为每个 Agent 写入期望速度。
06AgentNeighbourSystem收集附近代理，为 ORCA 避障准备邻居数据。
07AgentAvoidanceSystem计算避障后的实际速度；无避障组件时直接传递期望速度。
08FlowFieldAgentMovementSystem移动代理，并进行最终的静态障碍安全处理。

顺序保证 FlowFieldClearanceSystem 位于 CheckObstaclesSystem 之后、FlowFieldSystem 之前；FlowFieldSteeringSystem 位于 FlowFieldSystem 之后；最终移动发生在避障速度生成之后，从而保证每一阶段读取的都是正确版本的数据。
